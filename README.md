# 县域农村自建房安全巡查整改补助平台

面向县域治理场景的农村自建房安全管理系统，将**巡查、复核、告知、整改、安置、补助、验收、销号**放在**同一栋房屋档案**中闭环管理，并把风险告知、人员转移、补助资格和施工验收做成互相制约的规则，避免“数量销号、风险仍在”。

- 前端：Vue 3 + Vite + Element Plus + Pinia + Vue Router
- 后端：NestJS 10 + TypeORM + Passport/JWT
- 数据库：PostgreSQL 15

---

## 一、一键启动（Docker Compose，推荐）

要求已安装 Docker 与 Docker Compose 插件。

```bash
docker compose up -d --build
```

启动后：

| 服务 | 地址 |
| --- | --- |
| 前端页面 | http://localhost:8080 |
| 后端 API | http://localhost:3000/api |
| PostgreSQL | localhost:5432（用户 rural / rural123 / 库 rural_safety） |

后端首次启动会自动建表并写入演示种子数据（用户、施工队、两栋不同风险等级的房屋及初始巡查记录）。

停止与清理：

```bash
docker compose down          # 停止（保留数据）
docker compose down -v       # 停止并删除数据库卷（恢复初始种子）
```

## 二、本地开发启动

### 1. 准备数据库

```bash
# 自建 PostgreSQL 15
createdb -U postgres rural_safety
psql -U postgres -d rural_safety -c "CREATE USER rural WITH PASSWORD 'rural123';"
psql -U postgres -d rural_safety -c 'GRANT ALL ON SCHEMA public TO rural;'
```

> PostgreSQL 15 默认禁止普通用户在 public schema 建表，上面的 GRANT 不能省。

### 2. 启动后端（端口 3000）

```bash
cd backend
npm install
cp .env.example .env          # 按实际情况改 DB_HOST/DB_PORT
npm run start:dev
```

### 3. 启动前端（端口 8080）

```bash
cd frontend
npm install
npm run dev
```

前端开发服务器已配置 `/api` 代理到 `http://localhost:3000`（可用 `VITE_API_TARGET` 覆盖）。

## 四、业务流程与关键规则

### 风险规则引擎（巡查登记时自动判定，命中多条取最高级）

- 地基严重沉降 → **紧急转移**
- 擅自加层且 ≥4 层；承重墙严重开裂且擅自加层 → **紧急转移**
- 墙体严重开裂 → **暂停使用**
- 经营/出租且屋面严重渗漏；经营/出租为老旧土木结构（1990 年前） → **暂停使用**
- 擅自加层 → 限期拆除；屋面严重渗漏 → 限期修复
- 轻微裂缝/渗漏/沉降 → 一般关注定期复查

### 闭环流程（一栋一档）

```
网格员巡查登记（自动判定风险）
  → 乡镇住建复核（可调整等级，自动生成风险告知书）
  → 整改方案（拆除违建加层/加固承重墙/修复屋面/清退经营租户/设置警示/临时安置；
             自动生成限期整改通知书，高风险同时生成暂停使用通知、紧急转移通知）
  → 告知签收（农户可签收；拒签则留置送达留痕）
  → 现场封停确认（高风险必须真正停用）
  → 临时安置与实际转移确认（含人员构成：老人/租户/经营者）
  → 农户提交施工计划+补助申请（困难类型/权属/预算/施工队资质四项校验）
  → 乡镇初审（核验权属与困难情况）→ 县级核定 → 发放
  → 施工队上传材料（品牌/规格/批次/合格证）、照片、阶段进度，标记整改项完成
  → 乡镇按整改项逐条验收（可一次不通过→返工→复验）
  → 整改后复查（风险须明显下降）
  → 县级九项前置核查全部满足后销号
  → 复查发现问题反弹：销号记录“反弹重开”，档案重新进入治理流程
```

### 互相制约（已在后端强制实现，非仅前端提示）

1. 方案未下达不能启动整改；施工完成标记前不能验收。
2. 验收必须按方案**逐项**确认，缺项、缺现场照片一律拒绝；方案要求停用/安置而未落实的，验收不能通过。
3. 存在未查实处置的“偷换材料”事件时验收不能通过；该类事件不填写返工/更换材料的处置结果不能化解。
4. 存在“农户拒绝整改 / 租户不愿搬离”未化解事项时，不能确认人员转移完成（须先记录村干部、老人家庭成员、租户、经营者、施工队等参与方的协商过程）。
5. 人员未实际转移不能通过紧急转移房屋验收；验收未合格，安置人员不能返回居住。
6. 补助四项校验：
   - 无困难类型（低保/特困/脱贫不稳定/因灾因病因学突发困难）不予补助，各类困难设补助上限；
   - 房屋权属须有材料且经乡镇现场核验；
   - 预算明细须完整、金额不为 0 且不超上限；
   - 施工队须登记、证照有效、未列入黑名单、资质等级满足整改项要求（拆除加层/承重墙加固需乙级及以上）。
7. 未核定通过的补助不能发放，已发放的不能重复发放；补助申请未全部结案（在途）不能销号；核定通过但未发放也不能销号——**补助必须真正发给符合条件的家庭**。
8. 县级看板不只统计销号数量，还展示：高风险房屋是否真正封停停用、紧急转移人员是否实际转移（含验收后返回）、已发补助金额与驳回情况、未化解协商事项，并可按乡镇与风险类型查看治理进度。

### 异常/协商事项类型

农户拒绝整改、施工队偷换材料、补助资格争议、雨季风险加重、租户不愿搬离、验收不通过、复查问题反弹，均可在房屋档案内登记、多次追加协商记录并化解；雨季加重与反弹会把档案自动打回待巡查状态。

## 五、验证方式

### 自动化端到端验证（已实际执行）

在后端运行的前提下：

```bash
python3 scripts/e2e-check.py
# 如后端不在本机 3000：
# API_BASE=http://localhost:3000/api python3 scripts/e2e-check.py
```

脚本以五类角色真实登录并依次验证：数据隔离、规则引擎命中、越权拦截、租户不搬→协商→转移的制约、黑名单/超限补助拦截、无困难类型驳回、偷换材料拦截验收、逐项验收缺项/缺照拦截、验收不通过返工复验、九项销号前置、反弹重开、看板统计口径。

**本次交付前实际执行结果：`E2E 结果：120 通过 / 0 失败`**（后端连接本地 PostgreSQL 15，全新种子库，脚本退出码 0）。

另已实际执行的验证：

- `cd backend && npx nest build` 编译通过；
- `cd frontend && npx vite build` 构建通过，并以 `vite preview` 验证页面与静态资源可访问（HTTP 200）；
- 手工核对关键 API 返回：登录鉴权、房屋一栋一档聚合接口、看板 overview / by-township 统计。

> 说明：当前沙箱无 Docker daemon，未实际运行 `docker compose build`；Dockerfile/compose 配置采用 Node 20 Alpine + Nginx 标准多阶段构建，首次在装有 Docker 的机器上执行 `docker compose up -d --build` 即可。

### 建议手工演示路径（约 5 分钟）

1. 用 `grid` 登录 → “房屋档案 → 巡查登记”，把“地基沉降”选为严重，提交后可见自动判定为紧急转移与命中规则。
2. 用 `township` 登录进入房屋 NF-2026-0001：复核 → 制定方案（勾选全部整改项）→ 封停确认。
3. 用 `grid` 登记“租户不愿搬离”，尝试“确认转移”会被拦截；追加协商记录并化解后转移成功。
4. 用 `farmer` 签收文书、提交补助申请（可先选“黑马施工队”看校验标红，再换安固队）；`township` 初审核验权属、`county` 核定发放。
5. `crew` 上传施工材料、标记整改项完成；`grid` 登记“偷换材料”，观察验收被拦截。
6. 处置化解后，`township` 逐项验收（先选一项不合格体验返工），`grid` 整改后复查。
7. `county` 打开“销号核查”，九项全绿后销号；再由 `grid` 登记“复查问题反弹”，档案自动重开。
8. `county` 在“治理看板”查看按乡镇、风险类型的进度与高风险停用、补助发放实情。
